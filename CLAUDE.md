# Campaign Command Center

Static campaign dashboard for True Lean Solutions / TechTranspire, published to GitHub Pages and refreshed daily from Zoho CRM.

## Layout
- `site/boxbyte.js` (`window.__BOXBYTE__`): the latest Box Byte batch file (datasets `boxbyte_leads`, `boxbyte_messages`, `boxbyte_held`), kept on the orphan `boxbyte-snapshot` branch and copied in by the workflow. The data layer merges its datasets into `data.js`'s.
- `site/courier.js` (`window.__COURIER__`): the Medical Courier prospects sheet (datasets `courier_sends`, `courier_file`), kept on the orphan `courier-snapshot` branch and copied in by the workflow. Company names and outreach flags only.
- `site/research.js` (`window.__RESEARCH__`): dataset `wi_research`, decision makers found by web research for target accounts with no other contact in Zoho (name, title, company, public LinkedIn URL, source, source date, confidence). Kept on the orphan `research-snapshot` branch and copied in by the workflow; the page treats it as empty when missing. A Zoho contact with the same name at the same account replaces the research entry.
- Dataset `wi_mack`: Mack's LinkedIn connections whose current company is a target account (name, position, company, public LinkedIn URL, connected-on date, matching Zoho contact ID), built from his LinkedIn data export with emails dropped. Readable only on the private Claude Dashboard artifact; elsewhere it travels sealed (see `scripts/seal.mjs`) on the `linkedin-snapshot` branch and reaches the public site only inside the passcode lock. The page treats it as empty when missing.
- Dataset `li_sync`: Zoho contact ID and connected-on date for every confident match between Mack's LinkedIn export and a Zoho contact (exact first and last name, company not contradicting). IDs and dates only. Carried as `linksync.js` (`window.__LINKSYNC__`) on the orphan `linkedin-snapshot` branch and copied in by the workflow, so it reaches the public site only inside the passcode lock. The page treats it as empty when missing.
- `artifact/b2b-today.js` and `artifact/b2b-today.css`: source of the B2B Today tab, shared by the private Claude Dashboard artifact (minified and uploaded as `files/b2b-today.js` and `files/b2b-today.css`) and the passcode-locked public site (the workflow copies them into `site/`; they are gitignored there). The page script must load before them (they use `CC_RULES`, `CC_IND`). On the public site `window.CC_MAIL_PRIVATE = true` makes the Email card say the history is on the private dashboard only.
- `artifact/fn-engine.js`, `artifact/fn.js` and `artifact/fn.css`: the Founder Network tab on the private Claude Dashboard only (uploaded as `files/fn-engine.js`, `files/fn.js`, `files/fn.css`; script tags after `network.js` and the stylesheet link are in the artifact's `index.html` only, never in `site/index.html`). `fn-engine.js` is pure functions (no network, no writes) shared by the page (`window.FN_ENGINE`) and the Node tests.
- `scripts/fn_import.py` (Python standard library): builds the Founder Network file datasets from a scratch folder (`telegram`, `fireflies`, `outlook`, `sources`); removes phone numbers and email addresses from text, keeps Outlook to dates, counts, flags, the other side's domain and a 15-word note. Its inputs and outputs (the Telegram export, the reviewed roster, review notes, Fireflies pulls, Zoho emails used for matching) stay in a scratch folder, never in the repo.
- `tests/fn-engine.test.mjs`: Node tests for the engine on synthetic fixtures only.
- `artifact/qa.js` and `artifact/qa.css`: source of the Quality Assurance tab, shared like B2B Today (uploaded to the private Claude Dashboard artifact as `files/qa.js` and `files/qa.css`; the workflow copies them into `site/`, gitignored there). Load after the page script and `b2b-today.js`.
- `scripts/seal.mjs` (Node standard library): seals datasets for a public branch with the RSA public key `scripts/seal_key.pub.pem` (RSA-OAEP-256 wrapping a fresh AES-256-GCM key). Only the `MAIL_KEY` secret (the private key, never in the repo or a chat) opens them. Not in use yet: it needs the RSA key pair (public key committed, private key as `MAIL_KEY`). Until then `wi_mack` (names and LinkedIn URLs) stays off the public site; a sealed file would go on its branch as `<name>.sealed.json`.
- `scripts/lock_site.mjs` (Node standard library): run by the workflow with the `DASH_PASSCODE` secret; opens any `site/*.sealed.json` with `MAIL_KEY` (served as `window.__SEALED__`), then encrypts `data.js`, `boxbyte.js`, `courier.js`, `research.js` and the opened datasets into `site/data.lock.json` (AES-256-GCM, PBKDF2-SHA256 600,000 iterations, fixed salt so a remembered device stays unlocked across daily builds), deletes the readable files and strips their script tags. It fails, and nothing is published, when the secret is missing or shorter than 16 characters. The page shows a passcode gate (`gateOrLoad` in the data layer), can remember the derived key on the device (`localStorage` key `cc-unlock-v1`), and has a Lock this device button. Run locally with a plaintext `data.js`, the page skips the gate.
- Datasets `b2b_mail` and `b2b_mail_weeks`: email history with B2B campaign contacts from the team Outlook mailboxes (info@, hemang@, mack@, shruti@), matched to Zoho contacts by email address (Zoho contact ID, last email each way, who sent ours, counts, bounced flag; weekly sent/received counts). Dates and counts only: never subjects, message text, recipients or email addresses. On the private Claude Dashboard artifact, and carried as `mail.js` (`window.__MAIL__`, written by `scripts/b2b_mail.py jsfile`, which refuses any field that isn't an ID, date, count or flag) on the orphan `mail-snapshot` branch, which the scheduled mail tasks force-push; it reaches the public site only inside the passcode lock. B2B Today says the email history isn't in the build when missing. Built by `scripts/b2b_mail.py` (`rebuild` from per-contact searches, `merge` for each day's new mail; message IDs kept only as one-way hashes for weekly dedupe); a weekday scheduled task merges new mail and a Sunday task rebuilds. Its inputs and outputs stay in a scratch folder, never in the repo.
- Dataset `b2b_cal`: meetings with B2B prospects at Priority 1 or 99 on the team Outlook calendars (info@, mack@, hemang@, shruti@) in 2026, one row per meeting (Zoho contact ID, start time, cancelled flag, which calendars, matched `by` email or name) plus a row with `at` null for each prospect searched with nothing found. Times, flags and mailbox names only: never subjects, attendees, addresses or bodies. Built by `scripts/b2b_cal.py build` from per-contact calendar searches done by agents following `scripts/b2b_cal_task.md` (an event counts when the prospect's address is organizer, attendee or booking customer, or the subject names them; first-name-only bookings count when the first name is unique and 4+ letters; internal prep/review/reminder notes and all-day events never count; copies on several calendars are one meeting, cancelled only when every copy is). On the private Claude Dashboard artifact as an uploaded file; carried as `cal.js` (`window.__CAL__`, written by `scripts/b2b_cal.py jsfile`, which refuses anything else) on the orphan `cal-snapshot` branch, which the weekday scheduled calendar task (6:07 AM CT) force-pushes; it reaches the public site only inside the passcode lock, and the page treats it as empty when missing. Search inputs and outputs stay in a scratch folder.
- `scripts/fetch_zoho.py`: pulls the datasets from Zoho CRM via COQL (`/crm/v7/coql`) and writes `site/data.js` (`window.__DASH_DATA__ = {...}`, loads from file:// and Pages alike). Python standard library only; no dependencies.
- `site/index.html`: the whole page (styles, data layer, charts). d3 v7.9.0 comes from cdnjs; everything else is inline.
- `.github/workflows/refresh.yml`: runs the fetch at 12:30 UTC (6:00 PM IST), on push to `main` and on demand, then deploys `site/` with `actions/deploy-pages`.

## Commands
- Fetch data: `python3 scripts/fetch_zoho.py` (needs `ZOHO_CLIENT_ID`, `ZOHO_CLIENT_SECRET`, `ZOHO_REFRESH_TOKEN`)
- Serve locally: `python3 -m http.server --directory site 8000`
- Test the Founder Network engine: `node --test tests/*.test.mjs`

## How the page is built
- The page code talks to a small `window.dash` data layer at the top of `index.html`: `dash.loader` turns each raw Zoho answer into rows, `dash.calc` derives values from datasets, `dash.data(id)` reads them, and `dash.onData(fn)` redraws.
- Dataset IDs in `QUERIES` (fetch script) must match the `dash.loader(...)` IDs in the page.
- Campaign membership: B2B tag `May 2026 - 100 B2B`, ICP tag `2026ICP` (contacts and accounts), Founder Network by Relationship Type, Medical Courier account tag `2026MedicalCourier`. Priority 9/11 excluded everywhere; Founder Network wins over tags. The tag constants live in `fetch_zoho.py` and `CC_RULES` in the page; keep them in step. Deals are sorted by Deal Type (`CC_RULES.dealKind`). Campaign tabs and the Overview's monthly bars count the open pipeline only (Identify, Discovery, Proposals, Hold; `CC_RULES.isOpen`); B2B leaves out lost agreements but keeps signed ones (`CC_RULES.notLost`). The Pipeline tab shows every deal.
- Backlog: each campaign tab has a Backlog card; the Overview opens with a roll-up of B2B, ICP and Founder Network (Medical Courier stays on its own tab) (`dash.calc('backlog')`, labels in `BL_TEXT`). Agreements come from Zoho Sign (`sign_docs`: referral agreements and `Akhani_LLC_MNDA`): a party is Signed once any copy is signed, otherwise the newest non-recalled, non-draft copy decides; Tech Transpire/True Lean test sends are ignored. Overdue tasks are credited to their contact's campaign. A deal is stale when open and not updated for 14+ days (`STALE_DAYS`). Courier send counts come from the prospects sheet. Every backlog item opens (Clear ones too), each count is the length of the list it opens (`rp_backlog_people`, `icp_backlog_people`, `fn_backlog_people`, `mc_account_list`), and drill tables link names to the Zoho record via the sixth column entry (`[module, idField]`, see `zohoUrl`).
- Deals tab (`drawDeals`): filtered by Deal Type chips (`dlKind`), board columns Proposals, Discovery, Hold, Identify, then Closed Won, Closed Lost, Closed Lost to Competition. Age is days since `Modified_Time` (CT); stale is 14+ days (`DL_STALE`). Amounts show only where set (`amount_known`), so totals are floors. Loss reasons come from `Reason_For_Loss__s` on the `deals` query.
- ICP tab analysis (`drawIcp`, `icData`): verdict, next steps, target math, a ranked "Who to ask for a meeting" list (connected, never met; scored on Priority, seniority, ICP fit, size, connected colleagues; problem-first opener per industry group in `IC_OPENER`), acceptance by segment, ICP fit of accounts (`IC_IND`, `IC_PARTNER`) and account coverage flags. Built from `icp_backlog_people` (Connected, Requested, Email Required, plus P1/P3 not requested) and `icp_account_list`. New-request queue caps each account at `IC_MAX_PER_ACCOUNT`. On the private dashboard an ICP contact Mack is connected to (`li_sync`, plus `wi_mack`) counts as Connected even when Zoho says Requested or nothing (including ICP contacts outside the backlog, from `wi_icp_people`), joins Who to ask with a note on the card, and gets a next step to fix LI Connect; a connection made in the last 30 days adds 10 to the ask score. Warm Intros' Data quality card shows how many of Mack's matched connections at targets Zoho marks Connected (`wiLiSync`) with a fix and drill list.
- LinkedIn sync across campaigns (`CC_LI`; inert when `li_sync` is empty, so the public site matches Zoho): `li_fixes_rp`, `li_fixes_fn`, `li_fixes_icp` list campaign contacts the export shows as connected while Zoho says otherwise (from `wi_b2b_people`, Founder Network rows of `wi_introducers`, and `wi_icp_people` with Priority from `icp_backlog_people`). `rp_contacts_li`, `fn_contacts_li`, `icp_contacts_li` move each of them into a Connected group of its own (`li_only`); `funnel`, `contact_breakdown`, `attention` and the ICP tab read these instead of the raw counts. The backlog adds them to Connected, never met (and B2B's no-Priority item), drops them from ICP's pending and not-requested items, and shows a per-campaign item, Connected on LinkedIn, not marked in Zoho (`li_unrecorded`), only when `li_sync` has rows.
- Warm Intros tab (`#wi`; model `WI` and calcs `warm_paths`, `warm_people`; UI `wiDraw`): one row per target account (ICP and Medical Courier by tag, plus B2B: the companies of B2B campaign contacts whose firm hasn't signed our referral agreement; deduped by account ID) with every way in Zoho records. Levels, strongest first: 1 Same company (a relationship contact linked to the account), 2 Already in (a campaign contact there who accepted or met us), 3 Industry peer (same `CC_IND` group; always Unverified), 4 Recorded introduction (Referred By on a deal at the account). Confidence is separate: Verified (meeting, accepted connection, signed agreement, won client deal or referral recorded), Supported (link only), Unverified (Client label without a won deal, a same-name account on another record, or industry alone). Usable paths rank before unverified ones, then by level. Same-name accounts (`CC_NAMEKEY`) are flagged, never joined. A Client-labeled contact tagged 2026ICP, or at a Medical Courier target, is a campaign contact, not an introducer; so is a B2B-tagged contact at a B2B-only target. Built from `wi_introducers` (every contact with a Relationship Type), `wi_b2b_people` (B2B campaign contacts), `wi_icp_people` (every ICP campaign contact, for the person to reach) plus the ICP/MC account lists, `mc_contacts`, `deals_tagged`, `referral_links` and `agreements`. Person to reach: on a B2B-only account reached through a connected contact, that contact; otherwise the most senior contact there not yet met, other than the introducer; when Zoho has none, the web-research person (`wi_research`), whose name links to LinkedIn (`wiReach`). Mack's network (`wi_mack`): a connection made before 2026 is Same company and Verified (it replaces an Already in path for that person); one made in 2026 is Already in and Supported, only when the person has no other path. ICP's ask cards and Account coverage rows carry a Warm path badge (`wiBadge`) that opens the account here. Requests sent and introductions accepted aren't in Zoho, so the page doesn't show them; the proposed Introductions module is described on the tab. Industry groups (`CC_IND`) are shared with the ICP tab.
- B2B Today (`artifact/b2b-today.js`): calcs `b2b_people`, `b2b_funnel`, `b2b_segments`, `b2b_actions`, `b2b_monday`, `b2b_weeks`, plus `b2b_mail_people` (email status per prospect: They wrote last, Gone quiet at 14+ days since our last email, No reply yet, Talking, Bounced, Never emailed, No address) and `b2b_queue` (the work queue plus a Reply item for each prospect who wrote last within 30 days and has no reply or follow-up task already queued). The page falls back to `b2b_actions` when the mail data is missing. Queue checks, so the list shows only real work: an open task for a Do Not Contact record, or more than `TASK_STALE` = 45 days overdue, becomes a “Close in Zoho” item; a reply or follow-up task becomes “Close in Zoho” when the mail data shows we emailed the person after the task was created (`open_tasks` carries `Created_Time`; other task kinds just note the email); a meeting ask is Priority 1 only (two-way conversation, connected, never met, no open task) and is dropped when a meeting is already scheduled (`mtg_people.next`); agreement chases skip Do Not Contact, signed partners and lost partnership deals, and say when the deal is on Hold; a stale deal with email in the last 14 days asks for the deal to be updated, not revived; a task subject that starts with a teammate's name (Mack, Shruti, Harsh, Hemang, Pulkit) shows as Named in the task. The view groups the queue to one row per person (`groupQueue`; clean-up items group on their own), with the rest listed under Also open on Do this next.
- B2B Today Partner Funnel Overview (section `#b2-pf`, first on the tab; dataset `b2b_all`: every contact tagged “May 2026 - 100 B2B”, Priority 9 and 11 included, unlike the rest of the tab; calc `b2b_priority_all`; groups in `PF_GROUPS`): a donut on the left, Partner Funnel rows P5, P3, P1, P99 (light to dark green) in the middle, Inactive & Restricted rows P9 and P11 (amber, red) on the right; each contact sits in one group by current Priority, so the groups add up to the total (No Priority set and any undefined Priority value get their own row when present). Priority 99 means signed partner, set by the team in Zoho. Selecting a slice, a row or the center highlights the group (`pfPick`) and opens its list; Reset view in the header (`pfReset`, disabled when nothing is highlighted) clears the highlight and closes that list. The SOP link (`PF_SOP_URL`) opens the B2B Priority Definition sheet.
- B2B Today scorecard (under the Partner Funnel Overview; dataset `b2b_added`, calcs `b2b_added_rows`, `b2b_scorecard`): new B2B partner prospects added to Zoho this calendar month (CT) against `ADD_TARGET` = 50. A contact counts in the month Zoho created it when it carries the B2B tag, isn't labeled only Client, and isn't a repeat (same LinkedIn profile, or same name at the same company); missing name, company or LinkedIn doesn't stop it counting but puts it on the fix list. Shows the count (red until the target is met, then green), a progress bar with a tick where the month should be by today (target × weekdays gone / weekdays in month), status (Behind, On track, Target met), still needed, pace per week over the remaining weekdays, this week vs last, last month's total, a Priority 5 backlog card at the top of the right column (`b2b_p5_backlog`: tagged contacts at Priority 5 now, separate from the target; red with Weak under `P5_WEAK` = 100, amber Building to `P5_STRONG` = 350, green Strong above), a four-month trend, and a fix list for additions that don't count. The SOP link is `ADD_SOP_URL`. Zoho's Created By is a shared login, so who added a contact isn't shown.
- B2B Today Priority 3 panel (under the scorecard; calcs `p3_state`, `p3_periods`; link `P3_SOP_URL`): six cards (backlog, untouched, pursued/pending, connected, Email Required, two-way conversations) from Zoho's current Priority and LI Connect (`b2b_people`). Stages follow the approved meanings: P5 backlog, P3 relationship development (weekly transfer from P5), P1 two-way conversation; P2 and P4 unused. Today / Week / Month come only from field-change history, dataset `p3_events` (one row per change: `contact_id`, `field` Priority or LI_Connect, `from`, `to`, `at`); balances are rebuilt from those changes, events count unique contacts at Priority 3 (two-way: Priority 3 to 1 while Connected). Without history the cells show — and the panel says why; nothing is estimated. Untouched is red until 0, Email Required gray (tracking only), two-way green.
- B2B Today Priority 3 queue (card `#b2-monday`, calc `b2b_p3_queue`; replaced the Monday P5 selection queue): everyone at Priority 3 with LI Connect and a next step, grouped untouched, connected (never met), met, requested, Email Required, Do Not Contact; within a group by partner evidence; filter chips per group, 10 a page.
- B2B Today account gaps (section `#b2-na`, between the Priority 3 panel and meeting frequency; calc `b2b_account_gaps`; SOP 002 link `PM_SOP_URL`): a Referral Partner deal needs an Account in Zoho, so it lists B2B prospects (not Do Not Contact) at Priority 1 or with any meeting (completed, scheduled, past and not marked Completed, or counted in Total Meetings) whose contact has no Account; an Account that is our own company (`OWN_CO`: Tech Transpire, True Lean) counts as none. Three compact tiles, each target 0 and red above it, open and close the list shown inline (collapsed by default; the note shows only while a list is open): No Account, Upcoming meeting with no Account (the part with a meeting still to come), and Referral Partner deal on the wrong Account (a deal whose Contact Name is a B2B prospect and whose Account is missing, ours, or not the contact's, including a contact with no Account). The section is red while anything is open and green at zero. Each row says what to fix in Zoho, pointing at the Account on their Referral Partner deal, or at an unlinked Referral Partner deal whose Account carries their name.
- B2B Today meeting frequency (under the Priority 3 panel, above the Email section; datasets `b2b_meetings` (Events linked by Who_Id to a B2B-tagged contact) and `b2b_cal` (team Outlook calendars); calcs `mtg_people`, `mtg_depth`, `p1_meet_plan`; `MTG_STAGES`; titled “P1 Meeting Frequency & Relationship Depth”): covers B2B prospects at Priority 1 now only (`MTG_PRIORITY`; `mtg_people` keeps every prospect and carries `priority`, since the queue, account gaps and B2B Deals Created use all of them). Today / This week / This month count prospects newly entering a stage (Never Met on the contact's Created_Time, later stages on the date of the meeting that reached them; CT, weeks from Monday). The change compares today's total with the same day last month (dash when that was 0); red when Never Met rises, green when 4+ rises, gray for the middle stages. Sparklines are the stage size at the end of each of the last 12 weeks, rebuilt from meeting and creation dates for today's Priority 1 prospects (Zoho keeps no Priority history, so people who have moved on, P99 included, aren't in past weeks). Drill tables show Assigned as the owner, since Contact Owner is the shared Transpire login. Who to talk to next (`#b2-mp`, its own section at the bottom of the tab, after Data that limits this page; calc `p1_meet_plan`, `AGAIN_DAYS` = 30) splits Priority 1 into Ask for a first meeting (no meeting held or booked; connected on LinkedIn first, then those who wrote last), Meeting booked, Talk to again (last meeting 30+ days ago, nothing booked), Met recently, plus Log in Zoho (Outlook meetings Zoho doesn't show as Completed that day, SOP 7); compact tiles open and close the list inline, collapsed by default.

Deals listed in `PM_RP_EXCEPTIONS` (deal ID and reason) count as the partner's Referral Partner deal whatever their Deal Type, by the team's decision; the row says so. Layout: Partners Met is a circle on the left, centered against the right column, and always shows all time; its ring is an SVG with one arc per group (green created, grey another kind of deal, red not created). Hovering or focusing an arc, or the matching card or line (All time only), lights that arc, dims the others and turns the center into a readout of the group (count, share of partners met); selecting it opens its list and keeps it lit while that list is open (`pmSel`, cleared by a MutationObserver on the shared drill); the center opens everyone. Chart colors dim the rest on hover and show a tip (`pmTip`, one floating tooltip that also follows keyboard focus); the right column holds the period chips, the two deal cards and the chart. Period chips (This week, This month, This year, All time; `pmPeriod`, default All time) count partners whose first completed meeting falls in the period (CT, weeks from Monday) and their deals as they stand today, so Created + Not created = Met in every period. With a period chosen, a column chart under the cards compares it with the four periods before it (`pmSeries`: weeks from Monday, calendar months or years, the current one to date): each column is the partners first met in that period, stacked green (deal created) over red (not created); the total, each color and the bar open their lists. - B2B Today “Referral Partner Deals — Closed Won” (section `#b2-rw`, right under B2B Deals Created; calc `rp_signed` from `deals`, `deals_tagged`, `sign_docs`, `mtg_people`): one panel with three boxes, Combined (grey), Other Partners (blue) and Founder Network (green), each with its signed-partner total and the 1 / 2 / 3 / 4+ meetings-before-signing breakdown (a 0 column appears only when a signed partner has none). - Mack's Network tab (`#mn`, private Claude Dashboard only; `artifact/network.js` and `artifact/network.css`, uploaded as `files/network.js` and `files/network.css`; the tab button, section and script tag are added to the artifact's `index.html` only, not to `site/index.html`): dataset `mack_network` (an uploaded JSON file, never in the repo or on a branch) holds every connection in Mack's LinkedIn export (name, public profile URL, title, company, connected-on date;
